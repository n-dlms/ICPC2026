# Research Notes: Scheduling with Batching and Setup Costs

**Date**: 2026-08-14 (Day 0)
**Author**: Ntokozo Dlamini (quotes verified against local .txt extracts)
**Purpose**: Inform the decode-batching / prefill-chunking decisions of the ICPC 2026 collaborative inference scheduler (Codeforces 2251). Our problem: every task pays a per-task setup cost S (once per prefill chunk, once per decode group); decode may batch m requests with duration from a piecewise-linear table `duration(m)`; batch members must share the same decode step; UP/DOWN FIFO transfers are automatic.

**Verification rule**: every claim below carries an exact quote from the extracted text files in `research/papers/*.txt` (file + line numbers). Claims without a quote are explicitly labeled as inference.

## 1. Papers Downloaded (Open Access / Author-Hosted)

### 1.1 Allahverdi, A., Ng, C.T., Cheng, T.C.E., Kovalyov, M.Y. (2008). "A survey of scheduling problems with setup times or costs." European Journal of Operational Research 187(3), 985–1032.

- **URL**: https://doi.org/10.1016/j.ejor.2006.06.060 (green OA via PolyU IR: `http://ira.lib.polyu.edu.hk/bitstream/10397/1269/1/SetupSurvey-2006%28June-19%29.pdf`)
- **Files**: `research/papers/Allahverdi2008-setup-survey.pdf` (507 KB), `...txt` (215 KB)
- **Why**: The canonical taxonomy of setup time/cost scheduling; defines batch setup models, batch vs job availability, family/GT models, and catalogs single-machine batch-setup results — the closest open-access equivalent of Potts & Kovalyov (2000) for our purposes.

Key insights:

1. Batch setup time (cost) is paid once per batch; families are given, batch formation is a decision: "A batch setup time (cost) occurs when jobs ... are processed in batches ... and a setup of a certain time or cost precedes the processing of each batch. ... A batch is a set of jobs of the same family. While families are supposed to be given in advance, batch formation is a part of the decision making process." (txt L133–137)
2. Group Technology (GT) = one batch per family, and NOT using GT is provably beneficial for tardiness: "His computational experiments revealed that total tardiness can be significantly reduced by removing the group technology assumption." (txt L490–493, describing Schaller et al. 2000)
3. Batch availability = all batch members complete together (our decode groups exactly): "According to the batch availability model, all the jobs of the same batch become available for processing and leave the machine together. In the job availability model, each job's start and completion times are independent of other jobs in its batch." (txt L145–149)
4. Batch sizes are a decision; optimal integer batch sizes can be obtained by solving a relaxed non-integer problem then rounding: "Mosheiov et al. (2005) suggested an O(n) rounding procedure to calculate integer batch sizes from a straightforward solution of the relaxed non-integer batching problem." (txt L536–540)
5. The batch-size decision is inherently hard even in toy form: "They proved that this problem is strongly NP-hard even if the batch size is 3 and the weight of each job is equal to its processing time." (txt L564–568, Yuan et al. 2005b, constant setup + fixed batch size)
6. Setup occupies the machine: "In setup time models, no job processing is possible on a machine while a setup is being performed on the machine." (txt L164–165); and setups may be anticipatory (done before the job/batch arrives) or non-anticipatory (txt L160–164).
7. A non-batch setup model is just the batch model with one job per family: "The corresponding model can also be viewed as a batch setup time (cost) model in which each family consists of a single job." (txt L158–159)
8. Bounded batch sizes are under-studied because optimal structure is complicated: "Problems with bounded batch sizes / ... / Complicated structure of an optimal solution" (txt L1868–1875, Table 10).
9. Single-machine problems are dominated by batch setups (3/4 of papers), the rest non-batch: "For single machine problems, three quarters of the papers considered batch setup times while only one quarter of the papers discussed non-batch setup times." (txt L1745–1747)

### 1.2 Agnetis, A., Billaut, J.-C., Pinedo, M., Shabtay, D. (2025). "Fifty Years of Research in Scheduling – Theory and Applications." HAL preprint (CNRS), hal-05133397.

- **URL**: https://cnrs.hal.science/hal-05133397v1/document
- **Files**: `research/papers/Agnetis2025-fifty-years-scheduling.pdf` (84 pp), `...txt` (248 KB)
- **Why**: Recent comprehensive survey (invited, published by premier scheduling authors) whose §3.8 "Batching and setups" is a trustworthy open-access digest of Potts & Kovalyov (2000) and the surrounding batching theory.

Key insights:

1. The s-batch vs p-batch dichotomy; our decode stage is p-batch-flavored, our prefill is s-batch-flavored: "In serial batching (s-batching), jobs of the same batch are processed one after the other, and a setup time occurs only at the start of each batch." (txt L1596–1597); "In parallel batching (p-batching) models, all jobs in a batch are processed and released together, and the processing time of a batch is the processing time of the longest job in the batch." (txt L1607–1610)
2. Family setups: "a setup occurs when the next job belongs to a different family ... In this scenario, each batch contains jobs of the same family." (txt L1605–1606) — batch formation is the solution structure, families are input.
3. Complexity cliff with weights: unweighted completion time with s-batching is polynomial, weighted is hard: "1|F = 1, s − batch, batch − avail| Cj can be solved in polynomial time by DP [Coffman et al., 1990], 1|F = 1, s − batch, batch − avail| wj Cj is strongly NP-hard [Albers & Brucker, 1993]." (txt L1612–1614)
4. The central structural theorem — there is an optimal job ordering, and batches are just cuts of that list: "in the optimal solution batches only contain consecutive jobs from the list. Accordingly, the only decision is at which jobs to cut off the list of jobs to form batches." (txt L1624–1626)
5. SPT ordering inside p-batches is optimal for weighted completion time (largest job sets the batch duration): "for 1|p − batch| wj Cj , it is possible to show [Brucker et al., 1998] that jobs should be considered in SPT order (so that a batch processing time coincides with that of the highest-indexed job in the batch)" (txt L1626–1628)
6. Unbounded capacity is the tractable regime: "Many single machine scheduling problems with p-batching are solvable in polynomial time (mainly when b ≥ n)." (txt L1615–1616); bounded b is genuinely harder and some remain open (txt L1629–1631).
7. The modern p-batch review pointer: "They have recently been addressed by means of numerous approximation or meta-heuristic algorithms, as reviewed in [Fowler & Mönch, 2022]" (txt L1634–1635).

### 1.3 Baker, K.R., Trietsch, D. (2009). "Research Notes for Chapter 13" (companion to *Principles of Sequencing and Scheduling*, Wiley). Author-hosted at Dartmouth/Tuck.

- **URL**: http://mba.tuck.dartmouth.edu/pss/Notes/ResearchNotes13.pdf
- **Files**: `research/papers/BakerTrietsch2009-notes-ch13.pdf` (2 pp), `...txt` (13.8 KB)
- **Why**: The chapter is "essentially identical to Chapter 10 of Baker's Elements of Sequencing and Scheduling (ESS). That chapter, in turn, relies on Webster and Baker (1995) with respect to single machine models." (txt L2–4) — a legal, author-hosted digest of the Webster & Baker (1995) results that we cannot otherwise access.

Key insights:

1. Shortest weighted processing time (SWPT) is preserved *within* a family, even across batches: "SWPT applies within a set of consecutive jobs of the same family" (Bruno & Sethi, txt L16); "Monma and Potts (1989) showed that SWPT applies even to jobs of the same family that are processed in different batches." (txt L17–18)
2. Inter-batch ordering can be handled by a "pseudo-job" whose processing time is setup+work and whose weight is the set's total weight: "Mason and Anderson (1991) strengthened that result by showing that SWPT order should also apply to a pseudo-job that represents the set of jobs that may separate two batches from the same family. The processing time of the pseudo-job is the combined setup time and processing time of the set and its weight is the total weight of the jobs in the set." (txt L18–23)
3. The batch-size allocation result (our "allocation rule" question) traces to Santos & Magazine (1985) and Dobson, Karmarkar & Rummel (1987), as a special case of Property 3 of Webster & Baker (1995): "Theorem 13.3 is a special case of Property 3 from Webster and Baker, but in the limited form we presented in the chapter it is due to Santos and Magazine (1985) and was also obtained independently by Dobson, Karmarkar and Rummel (1987)." (txt L29–32)
4. The two-level (group-then-sequence) approach is only valid if the within-family sequence is optimal independent of the high-level sequence: "to work well, the two-level approach that we can employ under the GT assumption requires an efficient way to sequence jobs within each family such that this low-level sequence is optimal in any high-level sequence." (txt L54–56)
5. Under batch availability, teardown times add directly to setups: "In single-machine models with batch availability, teardowns have the exact same effect as setups and the two effects are additive." (txt L68–69)

### 1.4 Yang, F., Davari, M., Wei, W., Hermans, B., Leus, R. (2021/2022). "Scheduling a single parallel-batching machine with non-identical job sizes and incompatible job families." arXiv:2102.02002 (published in EJOR).

- **URL**: https://arxiv.org/abs/2102.02002
- **Files**: `research/papers/2102.02002-parallel-batching.pdf` (29 pp), `...txt` (63 KB)
- **Why**: p-batch scheduling with families where the batch duration is family-dependent — the closest published model to our decode group (batch of same-step requests, batch duration from table).

Key insights:

1. Batch atomicity and shared completion time (exactly our decode group semantics): "The processing time of a batch containing jobs from family j is qj , and the completion time of all jobs in a batch equals the completion time of the batch. Once the processing of a batch starts, there is no interruption and other jobs cannot be added to the batch before completion. A job cannot be split across batches." (txt L216–218)
2. Incompatible families (only same-family jobs batch together) make the problem a hybrid of bin packing and single-machine scheduling: "combinatorial problems, namely bin packing and single machine scheduling" (txt L19; the abstract's own phrasing).
3. Intuitive two-stage heuristics (pack per family, then sequence batches) are NOT trivially optimal — the paper's Example 1 shows three different values from three feasible groupings: "This example illustrates that an intuitive two-stage approach to BLSP consisting in first running a bin packing routine per family (where a bin equates with a batch) and then sequencing the batches, can" (txt L227–229, sentence continues in the paper).

### 1.5 Deppert, M.A., Jansen, K. (2019). "Near-Linear Approximation Algorithms for Scheduling Problems with Batch Setup Times." SPAA '19; arXiv:1810.01223.

- **URL**: https://arxiv.org/abs/1810.01223
- **Files**: `research/papers/1810.01223.pdf` (19 pp), `...txt` (101 KB)
- **Why**: Modern theory of setup-cost amortization across classes on parallel machines (our K clouds), including when splitting batches pays.

Key insights:

1. Setup is charged on class switch and not between jobs of the same class — the s-batch setup semantics: "A setup si is scheduled whenever a machine starts processing load of class i and when switching processing from one class to another different class on a machine. A setup is not required between jobs (or job pieces) of the same class." (txt L51–54)
2. "Small batches" (setup + work below OPT makespan) are a structurally favorable regime; the Monma–Potts heuristic: "list scheduling for complete batches followed by an attempt of splitting some batches" (txt L74–79).
3. Even with setups, near-linear approximations exist (ratio 3/2 for preemptive, 2 for non-preemptive in O(n)) — evidence that simple greedy/batch-first policies are near-optimal for makespan-type objectives (txt L21–37).

### 1.6 Li, S., Wen, Z., Wei, J. (2025). "Improved algorithms for single machine serial-batch scheduling to minimize makespan and maximum cost." arXiv:2503.23273.

- **URL**: https://arxiv.org/abs/2503.23273
- **Files**: `research/papers/2503.23273.pdf` (15 pp), `...txt` (39.5 KB)
- **Why**: s-batch with constant per-batch setup; the structural results and Pareto methods apply to trading off makespan-like (TDR) vs max-cost-like (SLO2/TPOT) criteria.

Key insights:

1. Setup per batch + batch-duration = sum + shared completion (our per-cloud decode model, modulo the table): "When a new batch starts, a constant setup time s is required for the machine. Jobs within each batch are processed sequentially so that the processing time of a batch equals the sum of the processing times of all jobs in the batch. All the jobs in a batch have the same completion time, namely, the completion time of the batch." (txt L37–41)
2. Bounded (b < n) vs unbounded (b ≥ n) capacity are the two canonical regimes (txt L42–45); Pareto-optimal enumeration over (Cmax, fmax) exists in O(n^3) for both — batching decision and sequencing decision can be separated in principle (txt L22–27).
3. "The order of jobs within a batch is immaterial due to the definition of the job completion times." (txt L46–47) — only group membership and batch start times matter.

### 1.7 Hermelin, D., Mnich, M., Omlor, S. (2019). "Single Machine Batch Scheduling to Minimize the Weighted Number of Tardy Jobs." arXiv:1911.12350.

- **URL**: https://arxiv.org/abs/1911.12350
- **Files**: `research/papers/1911.12350.pdf` (3 pp), `...txt` (52 KB)
- **Why**: batching with due dates (our SLO1/TDR target) — NP-hardness evidence and parameterizations.

Key insights:

1. Batching against due dates is a generalization of Knapsack and NP-hard even with few distinct parameters: "The 1|B, rj | wj Uj scheduling problem takes as input a batch setup time Δ and a set of n jobs ... the task is to find a sequence of batches that minimizes the weighted number of tardy jobs. ... as a wide generalization of Knapsack, it is NP-hard." (txt L15–19)
2. FPT tractability holds w.r.t. number of distinct due dates + weights etc. — not directly usable, but shows due-date-aware batching needs heuristics, not exact methods (txt L28–35).

### 1.8 Huertas, J.A., Van Hentenryck, P. (2025). "Constraint Programming Models For Serial Batch Scheduling With Minimum Batch Size." arXiv:2504.08793.

- **URL**: https://arxiv.org/abs/2504.08793
- **Files**: `research/papers/2504.08793.pdf` (10 pp), `...txt` (85 KB)
- **Why**: the *why batch* question phrased directly; minimum batch size models.

Key insights:

1. The raison d'être of s-batching: "s-batching is especially useful when grouping similar jobs can prevent repetitive machine setups, which are time-consuming and costly." (txt L30–32)
2. Same-family grouping minimizes setups: "To reduce these costly transitions, batches are usually formed using jobs from the same family, minimizing unnecessary setup operations." (txt L46–48)
3. Max batch size is usually a machine-capacity artifact, not a choice: "In the s-batch literature it is common to find maximum batch sizes due to physical capacities of the machines that process the batches." (txt L51–53) — in our problem there is NO max group size; any cap we impose is our own choice, and "Problems with bounded batch sizes" are precisely the hard-to-structure regime (Allahverdi Table 10, §1.1 insight 8).

## 3. MAPPING TO OUR PROBLEM

Our decode stage: group of m requests at the same decode step, run as one D PROC on one cloud, duration = `decode_proc(m)` from the table (decreasing sublinear in m, strictly positive), S paid once per group on every computer in the pipeline (P PRE/D PRE/D POST local S, D PROC cloud S, plus transfers). Prefill: one request per P PRE piece, S per chunk, chunking splits [0,num_layers).

**R1 — Model the decode group as a batch-availability batch; treat the group as atomic.** "All the jobs in a batch have the same completion time, namely, the completion time of the batch" (2503.23273 L40–41); "Once the processing of a batch starts, there is no interruption and other jobs cannot be added to the batch before completion. A job cannot be split across batches." (2102.02002 L217–218). Consequence: in the scheduler, a decode group is one task object: one S, one duration, one shared completion; members that join late do NOT join an in-flight group — the group closes at dispatch.

**R2 — Batching decision = choosing cut points of a sorted list, not choosing members arbitrarily.** "in the optimal solution batches only contain consecutive jobs from the list. Accordingly, the only decision is at which jobs to cut off the list of jobs to form batches." (Agnetis L1624–1626). For decode: sort ready same-step requests by a single key (e.g., deadline/SLO slack, or arrival order), and only consider *contiguous* groups of that order as candidates.
This reduces the decision space from partitions to thresholds — implement `BatchingPolicy` as "scan the sorted list, choose where to cut".

**R3 — Marginal-benefit rule for group size, computed from the duration table + S, then round.** The relaxed-batch-size-then-round approach is an established technique: "an O(n) rounding procedure to calculate integer batch sizes from a straightforward solution of the relaxed non-integer batching problem" (Allahverdi L537–539).
Concretely: for a candidate group of size m vs m−1, the gain of adding one more member is `[S + dur(m−1)] − [S + dur(m)]` of compute per group (setup amortization + sublinear table gain) minus the waiting cost of the added member and the delay imposed on the earlier members (they all finish together — R1). Batch only while marginal gain > marginal waiting cost. **Note**: the literature does not give us a closed-form threshold for sublinear-table durations; the marginal rule is the structurally sound form.

**R4 — Never impose group-size caps from above; caps are what make the problem hard.** "Problems with bounded batch sizes / Complicated structure of an optimal solution" (Allahverdi Table 10, L1868–1875); "Many single machine scheduling problems with p-batching are solvable in polynomial time (mainly when b ≥ n)." (Agnetis L1615–1616). There is no maximum group size in the problem statement; our own earlier idea of a cap m ≤ C is exactly the "bounded b" regime. Remove caps; bound only by R3's marginal rule and by TPOT/SLO pressure.

**R5 — Do not restrict to one group per cloud per step (no Group Technology).** "His computational experiments revealed that total tardiness can be significantly reduced by removing the group technology assumption." (Allahverdi L490–493). Splitting the same-step request set into multiple groups (different clouds, different sizes, staggered starts) is explicitly allowed (D PROC per cloud) and can be better than one giant group — the GT assumption (single batch per family) is the trap to avoid.

**R6 — Setup S is real machine time; schedule it as occupancy and treat it as sunk once the group starts.** "In setup time models, no job processing is possible on a machine while a setup is being performed on the machine." (Allahverdi L164–165); "When a new batch starts, a constant setup time s is required" (2503.23273 L37–38). Our state machine already charges busy_until += S + dur; keep this, and never schedule work on a computer during its S window (including transfer-queue time; transfers are FIFO and uninterruptible).

**R7 — Ordering rule for batches on a cloud: SWPT-like ("short work first") survives across batches.** "Monma and Potts (1989) showed that SWPT applies even to jobs of the same family that are processed in different batches." (Baker–Trietsch L17–18) and the pseudo-job construction (L18–23): when ordering consecutive decode groups on a cloud, compare pseudo-jobs (work = S + dur(group), weight = members' total weight); process smaller pseudo-work first when the FIFO queue otherwise allows.
In our pipeline the UP/DOWN FIFO order is fixed at dispatch time, so this constrains *which* group to dispatch next, not reordering in flight.

**R8 — Accept heuristic-grade batching; the exact problem is NP-hard even tiny.** "this problem is strongly NP-hard even if the batch size is 3" (Allahverdi L566–567, Yuan et al. 2005b); "as a wide generalization of Knapsack, it is NP-hard" (1911.12350 L18–19). With weighted objectives AND setups, "1|F = 1, s−batch, batch−avail| ΣwjCj is strongly NP-hard" (Agnetis L1613–1614). Therefore: no exact optimizer; a greedy marginal-benefit group builder + local improvement is the right engineering level, and any residual gap is shared by everyone in the contest.

**R9 — Prefill chunking is the mirror image: chunking splits a job into multiple batches, each paying S.** "A setup is not required between jobs (or job pieces) of the same class." (1810.01223 L53–54) holds for s-batch theory but NOT for us — the problem statement charges S per chunk, i.e., our chunks behave like separate classes. The theory's guidance on when splitting pays is the "small batches" regime: "list scheduling for complete batches followed by an attempt of splitting some batches" (1810.01223 L78–79).
Use that two-phase idea for chunking: start with whole-prefill (1 chunk), split a chunk only if the pipelining gain (compute/transfer overlap) exceeds the extra S — i.e., the huge_S / zero_S zoo cases decide automatically via the same marginal test as R3.

**R10 — Separate the two levels: membership decision (which requests, which group size) vs sequencing decision (when each group starts).** "the two-level approach that we can employ under the GT assumption requires an efficient way to sequence jobs within each family such that this low-level sequence is optimal in any high-level sequence." (Baker–Trietsch L54–56). Implement Layer 5 as: (i) a group builder (R2–R5) that only depends on ready set + table + S; (ii) a dispatch rule (R7) that decides group start times from cloud/FIFO state.
Verify each level's heuristic independently in the zoo (batching_trap: table flat ⇒ groups of 1; tpot_sensitive: w_tp large ⇒ larger groups).
