# 103 — Max-Flow / Min-Cost-Flow for Preemptive Scheduling with Release Times and Deadlines

**Claim.** For n jobs with processing requirements p_j, release times r_j, due dates d_j on m uniform parallel machines, a **feasible schedule exists iff the maximum flow in a time-expanded network equals Σ p_j**. The network's period nodes are the intervals between consecutive sorted milestones (release/due dates); all standard max-flow codes apply (O(t·n³) with a specialized flow, t = number of machine types; for identical machines this reduces to Horn's (1974) network procedure, O(n³)).
Weighted/utility criteria (max lateness, weighted completion rate, maximum utilization, i.e. minimizing the weighted max work in prescribed intervals) are optimized by **path-augmenting algorithms** on the same network — CAPA, a successive-augmenting-paths routine that iteratively pushes one unit along a label-derived path to the labeled job with the best marginal gain f(z+e_j) (Federgruen–Groenevelt, Management Science 1986). For **unit processing times** the flow is integral and the resulting schedule is automatically non-preemptive (p. 346, §2).

**Relevance.** This is the exact machinery for the batch/full-information re-optimization layer (doc-05 P2). Given the remaining requests at end-of-input (or at any re-plan epoch), a max-flow answers "which subset of requests can still complete on time?" and the min-cost-flow (SSP/CAPA) version answers "which subset maximizes Σ weight_j subject to feasibility?" with weights = our priorities (deadline-urgency, USA1 key, latency penalties).
Crucially for us: **unit-time models are polynomial and non-preemptive-integral** — the folklore statement "unit-job throughput with release times and deadlines on parallel machines = max flow; weighted = min-cost flow" (the assignment-to-slots reduction) is exactly the slot-booking problem in our occupancy arrays. It also gives the correct theory for the decode-grant feasibility test: `t + tokens_left·per ≤ D` (Solution.cpp:107) is a *serial* lower bound — the flow-based test is the *exact* parallel feasibility test and would tighten admission control.

**Algorithm sketch.** Network (Fig. 1, p. 343): s → job-node j, capacity p_j; job j → machine-period node (r, i) for every period i within [r_j, d_j], capacity ∞ (or per-machine type); (r, i) → period-node i, capacity (S_r − S_{r+1})·T_i (cumulative-speed difference × period length); period → sink, ∞. Feasible iff maxflow = Σ p_j. For weights: CAPA (§4, p. 347): label-propagate from source; choose the labeled target j maximizing f(z + e_j) − f(z); augment 1 unit; repeat — this is successive shortest paths with a concave marginal objective. Complexity O(t·n³·p_max) for the weighted criteria.

**Port plan.** New `-DMCF` stage, run at two points:

1. **Per-tick feasibility oracle (cheap version):** when the greedy admits a request, verify not just the serial bound but the flow bound over a *short lookahead window* (pending + in-flight work vs. remaining capacity in [t, min(D,T)]); reject if infeasible — tighter admission control, replacing the serial `est` check at Solution.cpp:135.
2. **End-of-input full-information phase:** after the last arrival is consumed, build the 2-resource time-expanded network (edge-slots and cloud-slots as two parallel resource layers, capacities Ecap/Ccap per tick, per-request chains with fixed comm offsets) over remaining WAIT + in-flight requests; run min-cost flow (unit weights = 1 per completable request, ε-weights for latency) to produce a *candidate completion set*; use it to decide which remaining requests to grant decodes to and in what order. **Transactional acceptance only**: re-validate the flow-derived plan with the exact simulator (`simulate_from`, Solution.cpp:203) before committing; flow is a candidate generator, never the source of truth (the chain model with comm and two resources is not exactly the paper's single-machine model).
- Complexity: n ≤ few thousand, T ≤ ~2000 (assumed scale) → Dinic/SSP over O(n + Ecap·T + Ccap·T) nodes is milliseconds per run; fits a tranche.

**Weaknesses / mis-transfers.**

- The paper allows **preemption**; our prefill is one non-preemptive block (though decode is token-granular ≈ preemptive per token — good), so the flow solution must respect block-start constraints: encode prefill as a single interval choice, not splittable work (this turns the pure-flow model into a network with one-of-many interval choices — still a valid flow formulation via interval-arc discretization, but no longer the paper's exact O(n³) bound).
- **Two-resource chains with fixed COMM offsets are NOT a single-machine/uniform-machine model**: the joint edge+cloud window structure must be encoded as a 2-layer network (each stage chooses (start_tick, resource) pairs with fixed relative offsets). The paper's guarantees don't transfer verbatim; treat the reduction as a template, verify with the local judge.
- Feasibility-with-deadlines via flow assumes *work can be placed anywhere* in [r,d]; our decode round trips are *serial* (tokens of one request cannot overlap), so the flow model overcounts parallelism — must add the serial chain constraint per request (which the network handles naturally if each request's flow path is one chain, but then it's assignment, not flow: matches the b-matching view of note 102).
- Offline result; in the online interactive phase it is only usable as a lookahead oracle; keep the greedy incumbent always.
- Weighted latency terms in the score are 1e-6-dominated; the primary lever is which requests complete on time (weight=1), secondary is ordering.
